# 13 – 식별된 흐름 전환: 도출된 흐름은 그대로, 폼·스킬·에이전트만 보강

**언제**: 요청이 "인계 기록에서 식별된 업무 흐름입니다" 로 시작한다. 프로세스 식별 화면이
실제 인계 기록에서 흐름을 도출했고, 그 흐름이 **이미 프로세스 폴더의
`process-definition.json` 에 들어 있다**(시스템이 첫 턴 전에 깔아 둔다).

**왜**: 이 흐름은 사람들이 실제로 일한 순서와 담당자다. 다시 그리면 인계 때와 다른 사람이
다른 순서로 일하게 되고, 같은 업무를 다시 전환할 때마다 흐름이 달라진다.

## 바꾸지 않는 것 (도출 구조)

- 단계(Activity)의 `id`·`name`·`role`, 에이전트가 맡던 단계의 `agent`·`agentMode`
- 게이트웨이의 `id`·`type`, 시작·종료 이벤트
- 연결(Sequence)의 `source`→`target` 과 분기값 `condition`
- 최상위 `roles`(endpoint 는 실제 담당자 id 다) 와 `processDefinitionName`

단계를 더하거나 빼거나 합치지 않는다. 분기값(`조건` 문자열)도 고치지 않는다 — 실행 때
직전 단계 폼에서 그 값 중 하나를 고르게 된다. 바꿔야 할 것 같으면 **바꾸지 말고** 마지막
채팅 한 줄에 이유를 적는다. 시스템이 검증·통합 때 구조를 도출 정의로 되돌리고, 되돌린
변경은 사용자에게 이유와 함께 보인다.

## 사용자가 이 방에서 흐름을 바꿔 달라고 하면

`request_human_input` 으로 묻지 않는다("새 설계로 전환" 같은 선택지도 내지 않는다 — 골라도
시스템이 도출 구조로 되돌린다). 정의를 고치지 말고 채팅 한두 줄로 답한다:
- 이 흐름은 인계 기록에서 관측된 담당자·순서라 전환 중에는 바꾸지 않는다는 이유
- 바꾸려면 저장한 뒤 프로세스 정의 편집기에서 고치면 된다는 안내

## 단계별로 하는 일

| # | 할 일 |
|---|---|
| 1 | **컨설팅·초안 승인을 하지 않는다.** `write_todos` 등록 후 프로세스 폴더의 `process-definition.json` 을 `read_file` 로 읽고 1단계를 완료로 표시한다. 파일을 새로 쓰지 않는다. |
| 2 | [03](03-elicit-artifacts.md) 그대로 후보를 묻는다. 단, **[에이전트] 후보는 `agent` 가 비어 있는 단계에만** 낸다(이미 에이전트가 맡던 단계는 그대로 둔다). 사람 단계에 붙는 에이전트·스킬은 초안을 돕는 용도다 — 담당자는 바뀌지 않는다. |
| 3 | [07](07-forms.md)·[08](08-reference-info.md) 대로 모든 단계 폼을 만든다. **배타 게이트웨이 바로 앞 단계 폼에는 나가는 선의 `condition` 값을 글자 그대로 선택지로 갖는 선택 필드**를 둔다. 정의에는 `tool`·`inputData`·`outputData`·게이트웨이 `conditionData` 만 `edit_file` 로 반영한다. |
| 4 | 정의를 다시 읽어 **바꾸지 않는 것** 목록이 그대로인지 확인한다. |
| 5 | 턴을 끝낸다. |
