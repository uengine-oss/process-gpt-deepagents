# 03 – Elicit Artifacts: 스킬/에이전트/DMN 후보 제시 + 선택 (HITL)

**목적**: 1단계에서 만든 프로세스 정의 JSON 을 분석해 **재사용 스킬 · 에이전트 · DMN
의사결정 후보**를 뽑고, 사용자에게 *무엇을 만들지* **한 번에** 묻는다. 사용자가 고른
것만 실제로 만든다. 이것이 이 skill 의 핵심 **HITL(Human-In-The-Loop)** 단계다.

산출물: 선택 결과를 받아 선택분만 스킬(skill-creator)/에이전트/DMN 으로 만들고,
`manifest.json` 에 매핑을 기록하고 `process-definition.json` 에 반영한다.

---

## 핵심 원칙

0. **🔴 반드시 "구체 후보를 담은 선택 질문"이어야 한다 (빈 질문/빈 후보 금지).**
   - 질문 **전에** 프로세스 elements 에서 종류별(스킬/에이전트/DMN) **구체 후보 3개 내외**
     를 도출한다(아래 "후보 도출 규칙"). 이 도출을 건너뛰고 질문부터 내보내면 안 된다.
   - **반드시 `request_human_input` 도구로** 묻는다(프로즈로 끝내지 말 것).
     후보는 **`question` 인자 하나에 아래 형식의 텍스트로** 담는다. `options` 인자를
     쓰지 않는다 — 프론트는 이 텍스트 형식을 파싱해 체크박스 패널을 그린다.

     ```
     이 프로세스에 추가할 항목을 골라주세요 (안 고르면 건너뜁니다)

     [스킬]
     • 휴가 잔여일수 검증: 신청 전 잔여 연차 확인 (활동 2개)
     • 결재 검토 처리: 신청서 기준 검토·승인 (활동 1개)
     • 결과 통보 발송: 승인/반려 결과 통보 (활동 2개)

     [에이전트]
     • 팀장 휴가 검토 담당: 검토·승인 자동 초안 작성
     • 인사팀 휴가 등록 담당: 승인된 휴가를 인사 시스템에 반영

     [DMN]
     • 승인 여부 판단: 승인 → 등록 / 반려 → 통보
     ```

   - **형식 규칙(어기면 패널이 안 그려진다)**
     - 섹션 머리글은 **대괄호만** — `[스킬]`, `[에이전트]`, `[DMN]`. 뒤에 다른 글자를
       붙이지 않는다.
     - 각 후보는 `• 라벨: 설명` 한 줄. 라벨과 설명은 콜론으로 구분한다.
     - 첫 줄(대괄호 없는 줄)이 패널 제목이 된다.
     - 후보가 없는 종류는 **섹션 자체를 만들지 않는다.**
   - 라벨은 **구체적이고 서로 다른 고유 이름**이어야 한다. "역할"·"규칙"·"자동화 요소"
     같은 일반 단어 금지.
   - 금지 예: "어떤 스킬/에이전트/DMN 을 추가할까요?"(후보 없음)·"…만들까요?"(예/아니오
     생성여부 질문) — 절대 금지.
   - 정말 도출되는 후보가 0개인 극히 예외적 경우에만, 질문 없이 "추가할 스킬·에이전트·
     DMN 이 없어 보입니다. 바로 폼·참조정보로 진행할게요" 라고 안내하고 다음 단계로
     넘어간다(빈 질문 금지).
1. **묻지 않고 다 만들지 않는다.** 후보를 보여주고 선택을 받는다. 아무것도 안 고르면 그
   종류는 건너뛴다. 강요 금지.
2. **한 번에 묻는다.** 스킬·에이전트·DMN 을 따로 여러 번 묻지 말고, **`request_human_input`
   한 번**에 세 섹션(있는 종류만)을 함께 담는다.
3. **후보는 JSON 에서 도출한다.** 지어내지 말 것. 아래 도출 규칙대로 실제 elements 를
   근거로 후보를 만든다.
4. **선택분은 하나도 빠짐없이 만든다.** 선택 개수와 생성 개수가 일치해야 한다.

## 후보 도출 규칙

> **추천 개수 목표**: 각 종류(스킬/에이전트/DMN)마다 **3개 내외의 후보를 적극적으로 추천**
> 하는 것을 목표로 한다(권장 상한 4개). 작은 선형 프로세스라도 재사용·자동화·판단 자동화
> 관점에서 의미 있는 후보를 발굴해 채운다. 후보가 정말 1~2개뿐이면 그대로 두고, 전혀
> 없으면 그 종류의 섹션 자체를 만들지 않는다. 후보는 반드시 실제 elements 에 근거해야
> 하며, 지어내거나 프로세스와 무관한 것을 넣지 않는다.

### 스킬 후보 (→ [04-skills.md](04-skills.md))
재사용 가능한 "공통 작업"을 찾는다. 근거:
- 여러 Activity 의 `instruction`/`description` 이 **유사한 의도**로 반복되면(예: "기준 대조 검토", "서류 확인") 그 묶음을 스킬 후보 1개로.
- 단일 Activity 라도 그 자체로 **독립적·재사용성 높은 절차**(예: "정책 기준 일치성 검증")면 후보가 될 수 있다.
- 후보 1개 = `{ id(safe_name kebab-case), label(한글 스킬명), description(1줄), source_activity_ids(근거 액티비티) }`.
- 후보가 없으면(작은 선형 프로세스) 스킬 섹션 자체를 만들지 않는다.

### 에이전트 후보 (→ [05-agents.md](05-agents.md))
"역할 + 그 역할이 반복 수행하는 스킬" 조합을 에이전트 후보로.
- 근거: `roles` 와, 각 역할이 담당하는 Activity 묶음. 스킬 후보가 있으면 (역할 × 스킬) 로 매칭.
- 후보 1개 = `{ candidate_id("agent_<역할>_<스킬>"), label("역할명 — 스킬명"), description("담당 활동 N개 · 역할/목표 요약"), role_name, activity_ids }`.
- **최종 승인·책임 소재·정책 결재처럼 사람 판단이 중요한 활동에는 에이전트를 붙이지 않는다.**
- 조직도 등 기존 에이전트 정보가 있으면 "기존 재사용" 으로 표시(신규 생성 안 함). 이 skill 의 일반적 상황(조직도 없음)에서는 전부 신규 후보.

### DMN 후보 (→ [06-dmn.md](06-dmn.md))

분기를 전부 DMN 후보로 올리지 않는다. **모든 분기는 기본적으로 `Sequence.condition`(BPMN 조건식)만으로 표현**하고, 그중 **의사결정 테이블로 분리할 재사용 가치가 있는 것만** DMN 후보로 승격한다.

**필요조건 (구조 — 아래 두 가지를 모두 만족해야 후보 자체가 성립)**:
- `type` 이 **ExclusiveGateway** 이다 (Parallel/Inclusive 는 제외 — 조건 평가 의미가 다름).
- outgoing Sequence 가 **2개 이상**이다.

**승격조건 (재사용 가치 — 아래 세 가지 중 하나 이상을 만족해야 실제 후보로 제시)**:
1. **로직 반복**: 같은 이름·유사 의도의 게이트웨이가 이 프로세스 안에 2곳 이상 등장하거나, 다른 프로세스/활동에서도 그대로 재사용될 만한 범용 판단이다 (예: "리스크 등급 판정", "결재 한도 판단", "휴가 승인 가능 여부").
2. **규칙 복잡도**: 분기 조건이 **3개 이상**이거나, 분기 조건 하나를 판단하는 데 **여러 입력 필드를 조합**해야 한다(단일 값 비교가 아니라 AND/OR 등 복합 조건).
3. **정책성·가변성**: 조직 정책·규정·기준액처럼 **코드 재배포 없이 운영자가 자주 바꿔야 하는 값/기준**이다 (예: "승인 한도 금액", "리스크 점수 임계치").

**제외(=DMN 후보로 만들지 않음)**: 단일 조건의 단순 2지 분기(흔한 "승인/반려" 판단 1개)이면서 위 세 가지 중 어느 것도 해당하지 않는, 이 흐름 안에서만 쓰이는 1회성 분기.

- 같은 이름의 게이트웨이가 여러 개면 **하나의 후보로 병합**.
- 후보 1개 = `{ candidate_id("dmn::<gateway_id>"), label("게이트웨이명"), description("분기 N개: 조건1 → 대상1 / 조건2 → 대상2 · 재사용 근거: <위 1~3 중 해당 사유 한 줄>"), gateway_ids }`. **description 끝에 반드시 재사용 근거를 한 줄 붙인다.**

## 선택 결과 처리

사용자 응답을 받은 뒤:

1. **스킬을 골랐으면** → [04-skills.md](04-skills.md) 로드 → 선택된 스킬만
   `task(subagent_type="skill-creator")` 로 생성 + JSON 반영.
2. **에이전트를 골랐으면** → [05-agents.md](05-agents.md) 로드 → `agents/<agent_id>.json`
   개별 파일 생성 + JSON 반영.
3. **DMN 을 골랐으면** → [06-dmn.md](06-dmn.md) 로드 → 선택된 게이트웨이를 top-level
   `dmn_decisions`/`dmn_rules` 로 생성 + gateway 연결.
4. 아무것도 안 골랐으면 → 바로 다음 단계(폼)로 진행한다.

> 처리 순서는 스킬 → 에이전트 → DMN 이 자연스럽다(에이전트 후보가 스킬과 엮일 수 있음).

### `manifest.json` (필수)

선택분을 만든 뒤에는 **반드시 프로세스 폴더에 `manifest.json` 을 `write_file`** 한다.
이 파일이 스킬·에이전트·DMN 을 실제 `activity`·`gateway` 에 연결하는 **핵심 매핑**이다 —
이게 있어야 마무리 단계가 `activity.skills`/`activity.agent`/`agentMode`/`orchestration`·
`dmn` 을 최종 정의에 빠짐없이 반영한다(누락하면 만든 산출물이 프로세스에 연결되지 않는다).

```json
{ "skills": [{"name": "<safe-name>", "activity_ids": ["..."]}],
  "agents": [{"id": "<agent id>", "activity_ids": ["..."]}],
  "dmn":    [{"id": "<dmn id>", "gateway_id": "<gateway id>", "decisions": [], "rules": []}] }
```

- `activity_ids` 는 **실제 수행 Activity 의 id** 다 — StartEvent/EndEvent/Gateway id 금지.
- 아무것도 선택되지 않은 종류는 빈 배열로 두거나 키를 생략한다.

## 멀티 프로세스일 때 — 한 번의 일괄 질문

여러 프로세스를 만드는 중([11-multi-process.md](11-multi-process.md))이면 **프로세스마다
따로 묻지 않는다.** `request_human_input` 을 **딱 한 번** 호출하되 `question` 에 아래
JSON 한 개만 넣는다:

```json
{"multi_process": true, "stage": "candidates",
 "processes": [
   {"name": "휴가 신청", "skills": [{"label": "...", "desc": "..."}], "agents": [...], "dmn": [...]},
   {"name": "경비 정산", "skills": [...], "agents": [...], "dmn": []}
 ]}
```

프론트가 이걸 프로세스별 페이지 질문으로 그린다. 응답은
`[프로세스명] 스킬: A, B / 에이전트: C / DMN: (없음)` 형식 줄들로 온다.
**모든 프로세스의 응답을 한 번에 받은 뒤** 각 프로세스 폴더에 선택 항목 전량을 생성한다.

- **프로세스 간 재사용**: 서로 다른 프로세스에서 고른 항목이 같은 의도면 중복 생성하지
  말고 같은 id 를 참조한다.

## 다음 단계 연결 (중요: 폼·참조정보는 자동 진행)

이 선택 단계는 **이 skill 에서 사용자에게 묻는 마지막 단계다.** 폼과 참조정보는 어떤
프로세스든 **항상 생성·연결해야 하는 필수 산출물**이므로, 여기서 *"폼을 만들까요?"*
같은 추가 질문을 **하지 않는다.**

선택을 반영한 뒤에는 **추가 확인 없이 곧바로** 아래를 **연속 자동 실행**한다:

1. 선택된 스킬/에이전트/DMN 생성 + `manifest.json` + JSON 반영 (위 "선택 결과 처리").
2. [07-forms.md](07-forms.md) 로드 → **모든 UserActivity 폼 자동 생성** + JSON 반영.
   (스킬/에이전트/DMN 을 하나도 안 골랐어도 진행한다.)
3. [08-reference-info.md](08-reference-info.md) 로드 → **inputData/conditionData 자동 연결**
   + JSON 최종 업데이트.

그런 다음 자체 점검·완료로 이어진다([09-service-execution.md](09-service-execution.md)).
단계 사이에 "다음으로 넘어갈까요?" 를 묻지 않는다.
