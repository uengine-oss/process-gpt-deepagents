# 11 – Multi-Process: 여러 프로세스를 한 세션에서 생성

**목적**: 작업 범위에 **독립된 프로세스가 2개 이상** 있을 때(한 문서에 별개 프로세스
여러 개, 여러 문서 업로드, 또는 사용자가 여러 프로세스를 요청), 각 프로세스를
컨설팅 → JSON 생성 → 후보 선택 → 폼·참조정보까지 빠짐없이 완성한다.

> **절차는 고정이다.** 진행 방식을 사용자에게 묻지 않는다 — 멀티 프로세스는 **항상
> 일괄(batch)** 로 §3 의 고정 절차를 따른다. 단일 프로세스와 마찬가지로 **사용자에게
> 멈춰 묻는 것은 정확히 2번**: (1) 일괄 컨설팅 승인, (2) 일괄 후보 선택.
> 프로세스마다 따로 묻지 않는다.

> 이 reference 는 [00-orientation.md](00-orientation.md)·[10-document-intake.md](10-document-intake.md)
> 에서 **"프로세스가 2개 이상"** 으로 판별됐을 때 진입한다. 1개뿐이면 이 파일을 타지 않는다.

---

## 1. 언제 이 단계를 타나 (멀티 프로세스 신호)

다음 중 하나라도 해당하면 멀티 프로세스 절차로 진입한다:

- **한 문서 안에 별개 프로세스가 여러 개** 있다. (서로 다른 제목·장(章)·SOP, 각자 독립된 시작/종료·목적)
- 사용자가 **여러 문서를 업로드**했고, 각 문서가 서로 다른 프로세스다.
- 사용자가 **여러 프로세스를 한 번에 요청**한다. 예: "구매 결재랑 출장 신청 둘 다 만들어줘".

### 별개 프로세스 vs 서브프로세스 (반드시 구분)
- **별개 프로세스**: 자기만의 트리거·종료·업무 목적·역할 묶음을 가지며 **독립적으로 실행 가능**하다 → 각각 별도 `process-definition.json`.
- **서브프로세스**: 하나의 큰 end-to-end 흐름의 **일부**다(부모 프로세스 안에 속함) → 별개 프로세스가 아니라 부모의 `subProcesses` 로 ([02-generate-definition.md](02-generate-definition.md)).
- 판별 기준: **하나를 떼어내도 다른 하나의 시작→종료가 깨지지 않으면** 서로 별개 프로세스다.

판별이 애매하면 지어내지 말고 **서브프로세스로 묶는 쪽**을 택한다(프로세스를 임의로 늘리지 않는다).

---

## 2. 산출물 폴더 — 프로세스별 네임스페이스

시스템 프롬프트가 지정한 프로세스 폴더 이름(예: `process-a1b2c3d`)을 첫 번째 프로세스에
쓰고, 두 번째부터는 **뒤에 번호만** 붙인다:

```
<base>/
├── process-a1b2c3d/          # 1번째 프로세스
│   ├── process-definition.json
│   ├── manifest.json
│   ├── skills/<safe-name>/SKILL.md
│   ├── agents/<agent_id>.json
│   └── forms/<activity_id>.form
├── process-a1b2c3d-2/        # 2번째 프로세스 (동일 구조)
└── process-a1b2c3d-3/        # 3번째 …
```

- ⚠️ 폴더명을 임의로 짓지 마라(`01-purchase-approval` ❌). 위 규칙을 벗어난 폴더는
  마무리 단계가 수집하지 않아 산출물이 사라진다.
- `index.md`·`01-consulting.md` 같은 **진행 추적 파일은 만들지 않는다.** 진행 상태는
  `write_todos` 로 관리한다.
- 각 단계 reference 가 말하는 `process-definition.json`·`forms/`·`skills/` 는 각
  프로세스 폴더 아래의 같은 경로를 뜻한다.

## 3. 고정 절차 (항상 일괄)

### 3-1. 컨설팅 일괄 — `request_human_input` **딱 한 번**

발견한 모든 프로세스의 상세 초안을 만들어 **한 번의 호출**로 묻는다. `question` 에
아래 JSON **한 개만** 넣는다(다른 문장을 섞지 말 것 — 프론트가 프로세스별 페이지
승인/반려 패널로 그린다):

```json
{"multi_process": true, "stage": "consult",
 "processes": [
   {"name": "구매 결재", "draft": "1. 구매요청 접수 (요청자) …\n2. …"},
   {"name": "출장 신청", "draft": "1. 출장계획 제출 (신청자) …\n2. …"}
 ]}
```

- `draft` 는 [01-consulting.md](01-consulting.md) 규칙대로 만든 **5~8단계 상세 초안**
  (단계 · 담당 역할 · 분기 · 반려 후 재신청까지).
- **범위(어떤 프로세스를 만들지)를 따로 묻지 않는다.** 사용자가 원하지 않는 프로세스는
  이 패널에서 반려하면 된다.
- 응답은 `[프로세스명] 승인` / `[프로세스명] 반려 - 사유` 형식 줄들로 온다.
  - 승인된 것만 만든다. 반려에 수정 사유가 있으면 그 초안만 고쳐 **다시 같은 형식으로
    한 번** 묻는다(승인된 것은 다시 묻지 않는다).
  - 전부 반려면 무엇을 바꿔야 할지 확인하고 다시 초안을 낸다.

### 3-2. JSON 일괄 생성

승인된 모든 초안을 [02-generate-definition.md](02-generate-definition.md) 규칙으로
각 프로세스 폴더의 `process-definition.json` 에 **한꺼번에** 만든다.
생성 결과는 프로세스별 한 줄씩만 짧게 보고(중간 JSON 덤프 금지).

### 3-3. 후보 일괄 질문 — `request_human_input` **딱 한 번**

각 프로세스의 [03-elicit-artifacts.md](03-elicit-artifacts.md) 후보를 도출해 **한 번의
호출**로 묻는다. `question` 에 아래 JSON **한 개만** 넣는다:

```json
{"multi_process": true, "stage": "candidates",
 "processes": [
   {"name": "구매 결재",
    "skills": [{"label": "구매요청 검증", "desc": "요청서 필수항목·예산 한도 확인"}],
    "agents": [{"label": "구매팀 검토 담당", "desc": "요청서 1차 검토 초안 작성"}],
    "dmn":    [{"label": "결재 한도 판단", "desc": "금액 구간별 결재선 결정"}]},
   {"name": "출장 신청",
    "skills": [{"label": "출장비 산정", "desc": "지역·일수 기준 여비 계산"}],
    "agents": [], "dmn": []}
 ]}
```

- 후보가 없는 종류는 **빈 배열**로 둔다(그 종류의 질문이 생략된다).
- 응답은 `[프로세스명] 스킬: A, B / 에이전트: C / DMN: (없음)` 형식 줄들로 온다.
- **모든 프로세스의 선택을 한 번에 받은 뒤** 다음 단계로 간다.

### 3-4. 이후 단계 일괄 실행 (추가 질문 없음)

모든 프로세스에 대해 **추가 질문 없이 연속 자동 실행**한다:

1. 선택된 스킬(skill-creator)·에이전트·DMN 생성 + 각 폴더 `manifest.json` 기록.
2. 모든 UserActivity 폼 `forms/<activity_id>.form` 생성([07-forms.md](07-forms.md)).
3. `inputData`/`conditionData` 연결([08-reference-info.md](08-reference-info.md)).
4. 각 프로세스 정의 자체 점검([09-service-execution.md](09-service-execution.md) 체크리스트).

끝나면 §5 최종 요약 한 줄만 남기고 턴을 끝낸다. 마무리는 모든 프로세스 폴더를 한 번에
처리한다.

---

## 4. 프로세스 간 재사용 (스킬·에이전트)

여러 프로세스가 **같은 의도의 스킬/에이전트**를 선택했다면 중복 생성하지 않는다:

- 앞 프로세스에서 이미 만든 스킬(같은 `safe_name`/의도)·에이전트(같은 `agent_id`)가 뒤
  프로세스에서도 선택되면 그 파일을 **각 프로세스 폴더에 동일 이름으로 복제**하고 같은
  id 로 연결한다(폴더 밖 공유 경로를 만들지 않는다 — 마무리 단계는 프로세스 폴더
  안만 수집한다).
- 사용자에게는 "같은 스킬을 두 프로세스에 연결했어요" 정도로만 알린다.

---

## 5. 최종 요약

모든 프로세스가 끝나면 **한 줄**로만 알린다:

> "프로세스 N개를 생성했어요. 확인 후 저장 버튼을 눌러주세요."

프로세스별 상세(단계 수·스킬·폼 개수)나 경로, JSON 은 채팅에 나열하지 않는다 —
산출물 패널이 프로세스별 탭으로 보여준다.

---

## 6. 주의

- **승인된 개수만큼만** 만든다. 문서에 잠깐 언급된 것을 임의로 별개 프로세스로 늘리지
  않는다(서브프로세스/단계일 수 있음).
- 각 단계에서 **장문 중간 요약을 반복하지 않는다.**
- 고정 절차(§3)의 순서를 건너뛰거나 섞지 않는다 — 컨설팅 일괄 → JSON 일괄 생성 →
  후보 일괄 질문 → 이후 일괄 실행.
- `request_human_input` 은 §3-1 과 §3-3 에서 **각 한 번씩만** 호출한다(프로세스마다
  따로 묻지 말 것).
- 멀티 프로세스라고 단계 규칙(02~08)을 느슨하게 적용하지 않는다 — 각 프로세스는 단일
  프로세스와 동일한 품질·구조로 만든다.
